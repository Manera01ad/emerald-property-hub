Date: 2026-10-29
Revision audited: `main` @ `2bc0965` ("Fixed blank-screen bug")
Live site audited: https://emerald-property-hub.lovable.app

Everything below is marked **verified** (I ran it or read the live system) or
**not verified** (I could not confirm it). Nothing is claimed to work without
evidence.

---

## 1. Summary

The application is in better shape than the roadmap suggests. The live site loads
on every route I probed, tests and the build pass, and the security boundaries I
could reach without credentials held. The problems are concentrated in four
places:

1. The nightly **Security** workflow has failed for five consecutive nights and is
   still failing. A correct fix already exists as an open draft PR (#6) but has
   not been merged.
2. The **hourly research scheduler is not verifiable from the repository**. The
   `cron.schedule(...)` job that calls the tick endpoint lives only in the
   database, not in any migration here. I could not confirm it exists or runs.
3. There is **no city/state model**. Geography is Chennai-only and hardcoded in
   several layers. Pan-India expansion is blocked on this, not on infrastructure.
4. **Observability is thin**: no external uptime or error monitoring, no
   scheduler dead-man's-switch, and no backup or rollback procedure is written
   down. Recovery is undocumented.

Recommended order: merge the already-written secret-scan fix; verify the
scheduler; add pure-logic foundations for expansion and disclosure; then decide
on monitoring and backups. The infrastructure that exists is adequate for current
traffic. No migration or platform change is justified yet.

## 3. Page-loading errors

**Finding: I could not reproduce a page-loading error on the live site.**

I requested `/`, `/explore`, `/properties`, `/map`, `/advisor`, `/compare`,
`/location-intelligence`, `/infrastructure`, `/research-services`, `/consult`,
`/contact`, `/auth`, `/admin`, `/my`, `/assistant`, `/properties/<valid-uuid>`,
`/properties/not-a-uuid`, `/sitemap.xml`, `/robots.txt`, `/mcp` and
`/api/public/research/tick`. Every application route returned 200 and the
rendered HTML was the real page, not the "This page didn't load" shell
(`grep -c "This page didn't load"` returned 0 for all).

Two things worth noting:

- **`/admin`, `/my`, `/assistant` return 200 with an ~18 KB shell.** These routes
  are `ssr: false` and redirect to `/auth` in `beforeLoad` on the client. A 200
  from `curl` on these paths proves only that the shell served — **not** that the
  auth guard worked. I could not verify the redirect without a browser session.
- **The historical blank-screen bug is fixed and the fix is present in two
  places.** `vite.config.ts` inlines a public Supabase URL and publishable key as
  a build fallback, and `src/routes/__root.tsx` calls `getPublicBackendConfig()`
  when the build-time values are absent. Both are in `main`, confirmed by the live
  200s.

The client-side error boundary (`src/routes/__root.tsx` `ErrorComponent`) and the
server-side HTML error page (`src/lib/error-page.ts`, wired through
`src/server.ts`) are both present, so a future failure should degrade to a
recoverable message rather than a blank screen. I did not force an error to watch
the boundary fire.

## 4. Architecture as built

**Stack.** TanStack Start (SSR) + React 19 + Vite, deployed by Lovable from
`main`. Database and auth are Supabase (project `dashpanandamjickoytj`). `main` is
production; there is no staging.

**Data access is in three layers, and the split is correct:**

- `src/integrations/supabase/client.ts` — browser client, publishable key, RLS applies.
- `src/integrations/supabase/client.server.ts` — service-role client, bypasses RLS,
  only imported from server functions and `.server.ts` modules.
- `src/lib/public-client.server.ts` — session-free publishable client for crawler
  paths (sitemap, property head metadata).

**Public visibility** is one rule, expressed once in SQL and mirrored once in
TypeScript: `status = 'published' AND listing_permission = true AND is_demo = false`.
Verified in `drizzle/migrations/0000_migration.sql` and `src/lib/visibility.ts`.
Every public query I found re-applies it explicitly, including the MCP tools and
the assistant tools, so an admin caller cannot leak a draft through those paths.

**Research engine** (`src/lib/research/`) is well-separated: pure rules in
`core.ts`, I/O in `engine.server.ts`, run only with the admin client from the
scheduler route or an admin-checked server function. It has a single-flight lease
(`lease_until`), a 50 s run timeout, a monthly cost cap, exponential retry backoff
(`1h, 2h, 4h…` capped at the normal interval), and idempotent upserts on
`(source_id, external_id)`.

**Scheduler auth** is sound: a 64-hex token in `private.scheduler_token`, checked
by a `SECURITY DEFINER` function granted only to `service_role`, and the route
additionally requires `^Bearer ([a-f0-9]{64})$`. Verified by reading the route and
migration 0004, and by the live 401s.

## 5. Reliability gaps for 24/7 operation

### 5.1 The hourly scheduler cannot be verified from the repository — HIGH

`drizzle/migrations/0004_research_engine.sql` creates the `pg_cron` and `pg_net`
extensions and the token, but **no migration here calls `cron.schedule(...)`**. I
grepped the whole repository and full git history: there is no `cron.schedule`
anywhere. The job that POSTs to `/api/public/research/tick` every hour is
configured directly in the database, outside version control.

Consequences:

- I cannot confirm the scheduler exists, is enabled, or targets the right URL.
  **Not verified.**
- If the job is dropped (database restore, project change), nothing in the
  repository restores it. There is no record of the correct statement.
- The endpoint answers `GET` with 200 HTML (the SPA fallback), because only `POST`
  is handled. A scheduler that used `GET` would look healthy while doing nothing.
  **Verified:** `GET /api/public/research/tick` returns 200.

### 5.2 No dead-man's-switch or external uptime check — HIGH

`research_ticks` records every call and the admin Research tab shows the last 50,
but that only helps someone logged in and looking. If the scheduler stops, the
site keeps serving and nobody is told. **Verified absent:** no monitoring service,
no alerting code, nothing in the workflows that checks the live site.

### 5.3 No documented backup or rollback procedure — HIGH

`AGENTS.md` forbids agents from applying migrations and says the owner runs them,
but no written procedure covers restoring the database, restoring one table, or
rolling back a bad deploy. Lovable has no staging and no separate deploy step, so
a bad `main` is a bad production. **Verified absent.**

### 5.4 Failures are mislabelled in one place — MEDIUM

`engine.server.ts` `runAgent` catches any error and sets
`r = { status: "success", items: 0, message: "Failed" }`, then overrides the
*stored* status to `failed`. The database row is correct, but the in-memory result
is misleading: the tick route maps `r.status` into its JSON response, so a failed
agent is reported as `success` in the body. **Verified by reading the code.**

### 5.5 Scheduler orchestration is not tested at all — MEDIUM

17 test files, all pure logic. There is **no test** for the tick route, for
`runDueAgents`, or for `runAgent`'s lease/backoff/cost behaviour. `core.ts` is well
tested; the orchestration around it is not. **Verified:** grep for
`runDueAgents|runAgent|tick` in `*.test.ts` returns nothing.

## 6. Correctness and consistency findings

### 6.1 `AGENTS.md` is out of date about the checks — LOW, but it matters

`AGENTS.md` and `.github/workflows/verify.yml` both say type-check currently fails
with "two type errors in plugin-generated files under `src/routes/`". **It
passes** (exit 0). The comment telling a future reader to "flip
`continue-on-error` to false once both are clean" is therefore half-satisfiable
today: type-check is already clean, only formatting is not. The formatting debt is
also understated: `AGENTS.md` says "roughly 2,300 unformatted spots"; lint reports
**2956 errors** and prettier flags **120 files**.

### 6.2 Migration numbering collision — MEDIUM

`drizzle/migrations/` contains **two files with the `0012` prefix**:
`0012_assistant_search_log.sql` (0 bytes) and
`0012_assistant_search_log_schema.sql` (the actual DDL). Drizzle-kit keys
migrations by prefix; a duplicate prefix is a trap for the next migration.
**Verified by `wc -l`.** Repository hygiene, not a database change.

### 6.3 No city/state model — HIGH for expansion

`public.properties` has a single free-text `location` column and **no city or
state** (verified in `types.ts` and migration 0000). Chennai is hardcoded in at
least five places: `src/lib/areas.ts` (`AREAS = { Chennai: … }`),
`src/lib/nearme.ts` (`AREAS["Chennai"]`), `src/lib/my-location.ts`
(`areaPoint("Chennai", …)`), `src/lib/constants.ts` (`MARKETS`), and page
titles/descriptions. `area_intelligence` is the one table that got this right:
`city` + `area` with `UNIQUE (city, area)`. See `docs/architecture-pan-india.md`.

### 6.4 Anonymous enquiry submission is unverified — HIGH if it is broken

Migration `0002` set the insert policy to
`WITH CHECK (status = 'new' AND admin_notes IS NULL AND assigned_consultant IS NULL AND consent = true)`.
My anonymous probe returned HTTP 400 (a schema-cache error on my test field) and
401 with an empty body. I did **not** cleanly verify whether a well-formed
anonymous enquiry succeeds, because I would not write test rows into production.
**Not verified.** This is the primary lead-capture path and should be tested
deliberately, with the owner's consent, before launch.

### 6.5 Production values inlined in build config — MEDIUM

`vite.config.ts` hardcodes the production Supabase URL and publishable key as
fallbacks. Both are public-by-design (`sb_publishable_…`, protected by RLS), and
the fallback is what fixed the blank screen. But the app will silently talk to a
hardcoded backend if build bindings go missing. The safer shape keeps the fallback
but asserts the value's shape, as `public-backend-config.ts` already does.

### 6.6 No Content-Security-Policy — MEDIUM

The live site sends HSTS, `referrer-policy` and `x-content-type-options`, but
**no CSP, no X-Frame-Options, no Permissions-Policy**. For a site that embeds
third-party iframes and will embed YouTube, a CSP is the control that limits what
an injected script can do. Adding one needs care (inline styles, the MapLibre CDN
load in `explore.tsx`, fonts), so it should be report-only first.

### 6.7 `.gitleaks.toml` on `main` is stale — MEDIUM

The allowlist names commits `c076bce` and `aa15b43`, but the scanner attributes
the findings to `dcc8fb5` (two Supabase publishable keys in `.env`), `aa15b43` and
`9375300` (the Maps browser key in `.env`), and `2059a443` (the publishable key
inlined in `vite.config.ts`). Four findings; the allowlist matches none of the
`vite.config.ts` case. PR #6 fixes this, and I verified the fixed scan passes.

## 7. Security review

Verified as correct: RLS enabled on every table with role-scoped policies; the
service-role client reachable only from server functions; the scheduler token
compared by a `service_role`-only function plus a route-level shape check; the
auth middleware validating three-part JWTs with `getClaims`; CSRF re-registered
explicitly in `src/start.ts`; the OAuth return-path helper rejecting
protocol-relative and control-character paths; public photo reads restricted to
photos of publicly visible listings by migration `0007`; anonymous enquiries
constrained to `status = 'new'` with no admin fields.

Needs attention:

- **The Google Maps browser key committed in `.env` has not been rotated.** PR #6
  says so itself. The file is untracked now, but the value is still in git history
  and readable by anyone with repository access. Rotate it in Google Cloud Console
  and restrict it to the PropWise domains. **This is the most concrete outstanding
  security action.**
- No CSP (§6.6).
